# Збір даних про затримки потягів УЗ

Пілотний проєкт: регулярно знімає дані з офіційного табло
[uz-vezemo.uz.gov.ua/delayform](https://uz-vezemo.uz.gov.ua/delayform)
і накопичує їх у CSV для подальшого аналізу.

Зараз мета — **тільки збір даних**. Візуалізація і публічна частина пізніше,
коли буде що показувати.

Версія 6. Що змінилось — див. розділ 6.

---

## 1. Що саме збирається

Сервер табло одразу віддає повний HTML з усіма потягами **і** переліком
станцій кожного рейсу. Станції приховані атрибутом `hidden`, клік на сайті
лише показує їх. Тому достатньо одного звичайного HTTP-запиту: без
headless-браузера, без імітації кліків, без прихованого API.

### Два типи збігу зі станцією

| Тип | Що означає | Звідки береться |
|---|---|---|
| `endpoint` | Місто — початкова або кінцева станція рейсу | колонка «Сполучення» |
| `transit` | Потяг лише проходить через місто | розгорнутий перелік станцій |
| `both` | І те, й інше | обидва джерела |

`transit` дає більше рейсів, але працює лише для тих потягів, у яких табло
взагалі показує перелік станцій (частина рядків його не має).

## 2. Файли в папці `data/`

| Файл | Логіка | Для чого |
|---|---|---|
| `snapshots.csv` | дописування, новий рядок лише коли щось змінилось | динаміка: як росла затримка в часі |
| `stops.csv` | дописування, новий блок лише коли змінились станції | де саме на маршруті накопичується затримка |
| `trips.csv` | перезапис, рядок на **примірник рейсу** | ГОЛОВНИЙ файл для аналізу: підсумок по рейсу |
| `stops_latest.csv` | перезапис, рядок на пару «рейс + станція» | ГОЛОВНИЙ файл для аналізу: актуальний стан по станціях, без повторів |
| `run_log.csv` | дописування, рядок на кожен запуск | контроль: чи запуск взагалі стався |
| `state.json` | службовий | пам'ять між запусками |

### Ключове: `trip_key` проти `instance_id`

`trip_key` = `номер | звідки | куди | дата` — це **маршрут**, він
повторюється щодня.

`instance_id` = `trip_key@дата-час першої появи` — це **конкретний рейс**
конкретної доби. Саме за ним агрегувати.

Дата відправлення на сайті показується не завжди, тому новий примірник
визначається за трьома ознаками (налаштовуються вгорі `scraper.py`):

- рейс був ВІДСУТНІЙ у табло на реальних запусках довше ніж `GAP_HOURS`
  (4 год). Саме відсутній, а не просто «минув час»: якщо на попередньому
  запуску рейс був у табло, то скільки б годин не минуло між запусками,
  це той самий рейс — ми просто не дивилися;
- затримка впала більше ніж на `DELAY_DROP_MIN` (90 хв);
- пройдених станцій стало менше щонайменше на `ROUTE_RESET_MIN` (3) —
  і лише за умови, що довжина маршруту не змінилась. УЗ час від часу додає
  чи прибирає станції в переліку; без цієї умови рейс помилково дробився
  надвоє (перевірено на реальних даних 22.09).

Причина, з якої створено примірник, пишеться в колонку `instance_reason` —
це дає змогу потім перевірити, чи не нарізало рейси помилково.

### Який файл для чого відкривати

Для звичайного аналізу («наскільки запізнився», «що по станціях») потрібні
лише два файли — `trips.csv` і `stops_latest.csv`. Вони перезаписуються
актуальними значеннями, повторів у них немає.

`snapshots.csv` і `stops.csv` — сирий архів із повторами. Це не помилка:
саме повтори дають динаміку («+1:20 → +2:30 → +4:15») і відповідь на
питання, на якому відрізку маршруту потяг втратив час. Заглядати туди
варто лише тоді, коли потрібна динаміка.

### Факт і прогноз — це різні речі

Для станцій, які потяг **ще не пройшов**, УЗ показує не справжній прогноз,
а поточну затримку, механічно скопійовану на всі станції далі за маршрутом.
Якщо потяг біля Лубен запізнюється на годину, на всіх станціях до кінцевої
стоїть +1:00 — незалежно від того, що там реально буде.

Для **пройдених** станцій відхилення — це факт. Але УЗ часто прибирає його
(показує прочерк) невдовзі після проходження.

Тому в `stops_latest.csv` факт і прогноз лежать у різних колонках:

| Колонка | Що означає |
|---|---|
| `value_type` | `fact` — є факт; `passed_no_fact` — станцію пройдено, але УЗ факт не показала; `forecast` — станцію ще не пройдено |
| `dev_fact_min`, `fact_time` | відхилення і час, побачені ПІСЛЯ проходження. Єдине, що можна вважати виміром |
| `dev_forecast_min`, `forecast_time` | останній прогноз, поки станцію ще не пройдено |
| `forecast_seen_kyiv` | коли зроблено цей останній прогноз |
| `passed_seen_kyiv` | перший запуск, у якому станція вже пройдена |
| `forecast_age_min` | хвилин між останнім прогнозом і проходженням — верхня межа «віку» прогнозу |

**Як користуватись:** для аналізу «де потяг втратив час» бери лише рядки з
`value_type = fact`. Рядки `passed_no_fact` можна використати з
застереженням, і лише якщо `forecast_age_min` малий (наприклад, до 30 хв):
прогноз, зроблений за 4 години до станції, мало що каже.

### Позначка завершення рейсу

Коли рейс зникає з табло, його рядок у `trips.csv` лишається назавжди і
отримує:

| Колонка | Що означає |
|---|---|
| `finished` | 1 = рейсу не було у 2 запусках поспіль |
| `finished_at_kyiv` | момент ПЕРШОЇ відсутності (не час прибуття!) |
| `final_delay_min` | остання зафіксована затримка перед зникненням |
| `last_stop_passed` | 1 = кінцева станція вже була позначена пройденою |
| `after_monitoring_gap` | 1 = у житті рейсу була довга пауза в спостереженні, ідентичність менш надійна |

Важливо: **зникнення з табло не дорівнює прибуттю**. Потяг міг прибути,
міг надолужити графік і випасти зі списку ще в дорозі, міг бути
скасований. `last_stop_passed = 1` — єдина пряма ознака, що він таки
дійшов до кінцевої. Між останнім знімком і зникненням є сліпа зона до
30 хвилин.

Якщо рейс зник, а потім знову з'явився (і розрив менший за `GAP_HOURS`),
позначка завершення автоматично скидається.

## 3. Налаштування перед запуском

Вгорі `scraper.py`:

```python
WATCH = ["КИЇВ", "ХАРКІВ", "ЛЬВІВ", "ДНІПРО", "ОДЕСА", "ПОЛТАВА"]
KEEP_ALL = True    # True = зберігати всі потяги, ігноруючи WATCH
```

`KEEP_ALL = True` стоїть навмисно: потягів у табло два-три десятки, місця це
майже не займає, зате фільтр можна буде переграти заднім числом, нічого не
втративши. Ключові слова — ВЕЛИКИМИ літерами, шукаються як частина назви.

Частота опитування — у `.github/workflows/scrape.yml`, рядок `cron`.
Зараз `"7,37 * * * *"` = кожні 30 хвилин.

## 4. Забрати дані собі

1. **Один файл**: відкрити `data/snapshots.csv` → кнопка **Raw** → Ctrl+S.
2. **Усе разом**: зелена кнопка **Code** → **Download ZIP**.
3. **Синхронізація**: `git clone` один раз, далі `git pull` перед аналізом.

Кодування UTF-8 з BOM — Excel відкриє з правильною кирилицею подвійним
кліком, без «Імпорту тексту».

## 5. Ризики і обмеження

### Гроші та інфраструктура

| Ризик | Наслідок | Стан |
|---|---|---|
| Приватний репозиторій: 2000 хв/міс безкоштовно, публічний — безліміт | Збір тихо спиняється в кінці місяця | Частота 30 хв ≈ 1440 хв/міс, влазить |
| Запуски за розкладом затримуються, частину задач GitHub відкидає | Дірки в даних | Cron на 7/37 хв; контроль через `run_log.csv` |
| Workflow вимикається після 60 днів без активності репозиторію | Збір спиняється | Щоденні коміти даних = активність |
| Workflow не в головній гілці | Cron не спрацює взагалі | Тримати в `main` |

### Технічні

- Якщо сайт змінить верстку — `run_log.csv` покаже `ok = 1` при
  `rows_total = 0`. Це сигнал, що парсер осліп.
- Якщо на runner'і не буде tzdata, час писатиметься в UTC. Колонка
  `tz_ok = 0` у `run_log.csv` це покаже (в workflow `tzdata` встановлюється
  явно).
- Сайт може поставити капчу чи блокування ботів. Так свого часу сталося з
  booking.uz.gov.ua. Плану Б немає.

### Змістовні — найважливіші

- **Історії «до» не існує.** Табло показує лише поточний момент. Усе, що не
  зняли, втрачено назавжди.
- **У табло потрапляють ТІЛЬКИ ті, хто запізнюється.** Пунктуальні рейси в
  дані не потраплять. Отже «відсоток вчасних прибуттів» за цим джерелом
  порахувати **неможливо** без окремого повного розкладу. Це головне
  методологічне обмеження проєкту.
- **Перелік станцій є не в усіх рейсів** — аналіз `transit` буде на
  неповній вибірці.
- **Колонка «Причина» майже завжди порожня.**
- **Затримка — це прогноз системи УЗ**, не зафіксований факт прибуття.
  На сторінці прямо написано, що вона розрахована автоматично й може
  змінюватись.

### Етичні та правові

- Державний інфраструктурний ресурс у воєнний час. Опитування частіше ніж
  раз на 15–20 хв не дає нічого корисного, але створює навантаження.
- Умови використання та `robots.txt` **не перевірені**. Варто зробити це до
  того, як збір стане постійним, і обов'язково до публікації.
- Перед оприлюдненням агрегованої історії руху потягів варто окремо
  подумати про безпекові наслідки.
